まず方向性の分岐

「常駐デーモンを自作するか」の前に、もう少し手前で大きく分かれる選択があります。

A. OS の機能に乗っかる(systemd timer / launchd / cron + 何らかのファイル監視) B. 既存のワークフローエンジンを使う(n8n, Huginn, Windmill, Prefect など) C. 自作デーモンを書く(Rust / Go / Python など)

「markdown でエージェントを簡単に追加」「ローカル」という要件だと、実は A と C のハイブリッドが一番素直だと思います。B は強力だけどブラウザ UI 前提のものが多くて、「markdown ファイルをポンと置く」運用とは思想が違います。
Rust で自作する場合の現実

Rust は確かに安定して常駐させやすいですが、このユースケースだと正直オーバースペックになりがちです。理由は、

    スケジューリングは結局 tokio-cron-scheduler みたいなライブラリに依存することになる
    LLM 呼び出しが入る以上、ボトルネックはネットワーク I/O で、言語の速度差は無関係
    markdown パース、フロントマター解析、ファイル監視、プロセス起動の取り回しは Python/Go の方が圧倒的に書きやすい
    「エージェント追加が簡単」を実現するには、設定の hot reload とかエラーの可視化とかの方が重要で、そこは言語選択より設計の問題

Rust が効くのは、何百ものエージェントを並列実行してメモリを切り詰めたい、みたいな状況です。個人利用なら Go か Python の方が開発速度的に幸せだと思います。
私なら採る構成

「markdown でエージェント定義 → デーモンが拾って実行」を素直に組むなら:

~/.agents/
├── daily-news-summary.md      # スケジュール: 毎朝7時
├── on-pr-opened.md            # イベント: webhook
└── watch-downloads.md         # イベント: ファイル監視

各 md ファイルはフロントマターでトリガーを宣言:
markdown

---
trigger: schedule
cron: "0 7 * * *"
---
今日のニュースを要約して Slack に投げて

markdown

---
trigger: file_watch
path: ~/Downloads
pattern: "*.pdf"
---
このPDFを読んで要点を Obsidian に保存して

デーモン側がやることは:

    ディレクトリを監視して md ファイルを読み込み・パース
    トリガー種別ごとにディスパッチャに登録(cron系・ファイル監視系・webhook系)
    発火時に Claude Code なり別の LLM CLI なりをサブプロセスで起動して、本文をプロンプトとして渡す
    ログを残す

これだけなら Python + APScheduler + watchdog + FastAPI(webhook用) で200〜300行で書けます。Go なら robfig/cron + fsnotify + net/http で同じくらい。
さらに手前の選択肢

実装する前に検討の価値があるのは、Claude Code 自体をスケジュール起動する という手抜き案です。systemd timer なり cron なりで claude -p "$(cat ~/.agents/daily-news.md)" を叩くだけ。デーモンを書かずに済みます。

イベントドリブンが要るならここに entr や watchexec を足す。これで7割の用途はカバーできて、足りなくなった時点で自作デーモンに移行するのが投資対効果的には良いと思います。

Windows での常駐方法

ここが Linux/Mac と違って面倒なところで、選択肢が3つあります。

1. Windows サービスとして登録する ちゃんとした方法。ログイン前から動く、自動復旧する、イベントログに統合される。ただし実装が面倒(Go なら kardianos/service、Python なら pywin32 経由、Rust なら windows-service クレート)。

2. スタートアップに登録した普通のプロセス ログイン後に起動する常駐プロセス。実装は楽だが、ログオフで死ぬ、UAC の扱いが微妙。個人利用の最初の一歩としては十分。

3. WSL2 で Linux デーモンとして動かす 開発者なら一番楽かもしれない。systemd も使える(WSL2 で systemd=true 設定)、Linux 用のツールがそのまま動く。ただし Windows ネイティブのファイル監視(C:\Users\... 配下)はパフォーマンスに難あり、Windows アプリとの連携も一手間。
言語選択の再評価

Windows サービス化を視野に入れると、Rust や Go の優位性が少し戻ってきます。

    Go: クロスコンパイル一発でシングルバイナリ。kardianos/service で Windows サービス化が10行で書ける。ファイル監視(fsnotify)、cron(robfig/cron)、HTTPサーバ全部標準的なライブラリで揃う。個人的にはこれが本命だと思います。
    Rust: 同じことはできるが書く量が増える。学習目的でないなら Go の方が早い。
    Python: pywin32 でサービス化はできるが、依存関係の配布が面倒(PyInstaller で固める手はある)。WSL2 で動かす前提なら全然アリ。

スタートアップ登録の具体策

3つやり方があります。

1. スタートアップフォルダにショートカット shell:startup で開くフォルダにショートカット置くだけ。一番簡単。ただしコンソールウィンドウが出る。

2. タスクスケジューラで「ログオン時」トリガー 推奨。コンソールを隠せる、失敗時の再起動設定もできる、ユーザー権限で動く。schtasks /create で一発登録できる。

3. レジストリの Run キー HKCU\Software\Microsoft\Windows\CurrentVersion\Run に登録。動くけど可視性が低くてメンテしにくい。

個人的には 2 のタスクスケジューラ をおすすめします。デーモンの初回セットアップ時に agent-daemon.exe install みたいなサブコマンドで自動登録するようにすると、ユーザー(自分)は何も意識せずに済みます。

Go でビルドするとデフォルトでコンソールウィンドウが付きます。常駐させるならこれは消したい。

最小構成の骨組み

イメージとしてはこんな感じです:

agent-daemon.exe
  ├─ main goroutine: シグナル待ち & 全体オーケストレーション
  ├─ watcher goroutine: ~/.agents/*.md を fsnotify で監視
  │                     変更検知でエージェント定義を再ロード
  ├─ scheduler goroutine: cron 系トリガーを管理

  └─ webhook goroutine: localhost:xxxx で HTTP 受付

エージェント定義の再ロードは、ファイル単位の差分更新ではなく「全部読み直して再構築」の方がバグりにくいです。エージェント数がせいぜい数十なら全然問題ない。

ただ一点だけ、ニュアンスを確認させてください。「at を考えたくない」を実装としてどう解釈するか、ふた通りあります。
解釈A: デーモン起動時刻を基準に相対実行

per 1 day → 起動した瞬間に1回動いて、そこから24時間ごと。基準時刻はバラバラ。

実装が一番楽。「いつ動くか」は「いつ起動したか」次第。
解釈B: 起動した「直後」に1回動いて、あとは間隔を守る

これは A と同じですね。
解釈C: 固定の基準時刻(例: 00:00)からの間隔

per 1 day → 毎日 00:00 per 6 hour → 00:00, 06:00, 12:00, 18:00 per monday → 毎週月曜の 00:00

予測可能性は高い。深夜に動かれるのが嫌な場合は別途オプションが要る。
個人的推奨: A

理由:

    実装が単純(time.Ticker 一発)
    「だいたい毎日1回動けばいい」という用途には十分
    厳密な時刻指定が要るユースケースは、要るときに後から at を足せばいい

つまり「per 1 day = 24時間ごと」「per 3 hour = 3時間ごと」と素直に解釈する案です。
文法案を詰める
yaml

schedule: per 1 day      # 24時間ごと
schedule: per 3 day      # 72時間ごと
schedule: per monday     # 月曜が来るたび
schedule: per 1 hour     # 1時間ごと
schedule: per 6 hour     # 6時間ごと

ここで気になる点をいくつか:

1. 単数/複数の扱い 英語的には per 3 days per 6 hours ですが、揺れると面倒なので 常に単数固定 が楽。per 3 day でいい、と割り切る。あるいは両方受け付けてもいいですが、ドキュメントは単数で統一。

2. per monday のタイミング 解釈Aだと「起動後、最初の月曜0時に発火、以降7日ごと」が自然。月曜の何時に動くかは、解釈Cを部分的に採用して 0時固定 にするか、解釈Aを貫いて「起動曜日基準」にするか。

月曜なら月曜の0時、が直感的なので、ここだけ解釈Cを混ぜるのが良さそうです。曜日指定で時刻を考えないなら 0時 か起動時刻のどちらかしかなくて、0時の方が分かりやすい。

3. per weekday per weekend は? 要らないと言われたら削ります。あると便利な気もしますが、ミニマルにいきたいなら削ってOK。

per <N> day        # N×24時間ごとに発火(起動時刻基準)
per <N> hour       # N時間ごとに発火(起動時刻基準)
per <曜日>          # 毎週その曜日の0時に発火

曜日は monday〜sunday(英語小文字)。

    スケジューラを書かなくていい(OS にやらせる)
    文法を決めなくていい(自然言語のまま)
    「毎日だけど祝日は除く」「月初の営業日」みたいな複雑な条件も、Claude が判断するから自由
    設計判断を全部「Claude のプロンプト」に押し付けられる

要するに、スケジューリングという問題を LLM に外注する という発想ですね。これは LLM ネイティブな解き方として正しいと思います。
構成

タスクスケジューラ(15分おき)
    ↓
claude.exe -p "agentsディレクトリを見て、今動かすべきものを判断して実行"
    ↓
Claude が ~/.agents/*.md を読む
    ↓
各エージェントの frontmatter にある「頻度の自然言語」と
~/.agents/logs/ の過去実行ログを照合
    ↓
動かすべきものだけ実行 & ログ追記

デーモンも Go コードも要らない。タスクスケジューラ1つと、ディスパッチャ役の Claude プロンプトだけ。
エージェント定義
markdown

---
name: morning-news
frequency: 平日の朝に1回くらい
---
今日の主要ニュースを要約して ~/Documents/news.md に追記して

markdown

---
name: weekly-review
frequency: だいたい週1、月曜あたり
---
先週の進捗を振り返って ~/Documents/weekly.md に追記

markdown

---
name: inbox-sweep
frequency: 数時間ごと
---
~/Inbox を整理して

frequency は本当に何でもいい。「気が向いたら」「月末に1回」「夕方くらい」とかも書ける。
ディスパッチャプロンプト(雛形)

~/.agents/_dispatcher.md みたいに置いておく:
markdown

あなたはローカルAIエージェントのディスパッチャです。

現在時刻: {{now}}

以下の手順で動作してください。

1. ~/.agents/ ディレクトリ配下の *.md ファイル(_で始まるものは除く)を全て読む
2. 各エージェントの frontmatter の `frequency` と、~/.agents/logs/<name>.log の最終実行履歴を照合する
3. 「今このエージェントを動かすべきか」を自然言語の頻度指定に従って判断する
4. 動かすべきと判断したエージェントについて、本文の指示を実行する
5. 実行したエージェントについて ~/.agents/logs/<name>.log に1行追記する
   形式: YYYY-MM-DD HH:MM:SS | <結果サマリ1行>

判断のガイドライン:
- frequency が曖昧でも、最終実行からの経過時間を見て妥当な判断をする
- 迷ったら動かさない(動かしすぎより、動かさない方が安全)
- 1回の起動で複数エージェントが該当することもある

タスクスケジューラ登録
cmd

schtasks /create /tn "AgentDispatcher" /tr "claude.exe -p \"$(cat %USERPROFILE%\.agents\_dispatcher.md)\"" /sc minute /mo 15

(実際は cmd だと変数展開がアレなので PowerShell でラップするか、.bat を経由するのが現実的)

15分おきに起動。Claude が毎回ログを見て「今は動かすタイミングじゃないな」と判断したら何もせずに終わる。コストは判断1回ぶんの軽い呼び出しで済みます。
この設計の良いところ

    設定が人間言語のまま「毎日朝」「週1」「月末」「気が向いたら」全部通る
    コードがほぼゼロ.bat と .md だけで動く
    拡張が異常に楽 新しいトリガー種別(例: 「天気が雨の日」「金曜の夕方」)も frequency に書くだけ
    デバッグも楽 Claude にログを読ませて「なぜ動かなかったのか」を聞ける

注意点・正直に言っておくこと

    判断ブレ LLM なので「毎日」と書いても日によって動いたり動かなかったりする可能性がある。重要なジョブには厳密性は期待できない。
    コスト 15分おきにディスパッチャを起動すると、1日96回 Claude を叩くことになる。判断だけなら安いですが、ゼロではない。Claude Code のサブスクで叩ける範囲か、API 経由なら課金が乗る。
    ログ管理 Claude にログを書かせる以上、フォーマットがブレる可能性がある。最初は「読めればいい」で割り切るのが吉。
    同時起動 タスクスケジューラの前回起動がまだ走ってる時に次が来る、みたいな状況の対策(/IT でインタラクティブ起動、または前回PID確認)は要検討。15分間隔なら大抵問題ないですが。

起動間隔の選び方

    15分: 「数時間ごと」「日次」用途には十分。1日96回。
    1時間: 「日次」「週次」中心ならこれで十分。1日24回。
    30分: バランス型。1日48回。

「frequency が時間単位」のエージェントが多いなら15分、「日次以上」しかないなら1時間で十分です。

確かに。実際の用途を考えると、

    ニュース要約 → 朝1回
    週次レビュー → 週1
    inbox整理 → 1日1〜2回
    ファイル整理系 → 1日1回

みたいなのが大半で、「1日に何度も動かしたい」エージェントってあんまり想像できないですね。それなら3時間でほぼ過不足ない。1日8回なら判断コストもほぼ無視できます。

ひとつだけ補足すると、3時間間隔だと「朝のニュース要約」が朝7時ぴったりには動かない、というのは織り込んでおいた方がいいです。起動タイミング次第で6時に動いたり9時に動いたりする。でも「朝のうちに動けばいい」くらいの粒度なら全く問題ないはず。

もし将来「ぴったりこの時間に動かしたい」が出てきたら、そのエージェントだけタスクスケジューラに個別登録する、で十分対応できます。ディスパッチャ方式は「ゆるい定期実行の母艦」と割り切る。
確定した設計

    ディスパッチャ起動間隔: 3時間
    エージェント定義: markdown + 自然言語 frequency
    ログ: Claude が書き込む
    判断: 全部 Claude に丸投げ

では実装に進みます。確認したいのが2点だけ:

    ログのファイル分割
        A案: ~/.agents/logs/<name>.log でエージェントごと別ファイル
        B案: ~/.agents/log.md で全エージェントぶんを1ファイルに時系列で
    A案の方が Claude が「このエージェントの最終実行はいつか」を判断しやすいので推奨ですが、B案の方が人間が眺めるには楽です。
    エージェント本文の実行方法 ディスパッチャの Claude セッション内で本文の指示も実行させる(同一プロセス)か、別途 claude -p を子プロセスとして起動させるか。 前者は楽だがコンテキストが混ざる。後者はクリーンだがディスパッチャに「子claudeを起動する」スキルが要る。 個人的には 前者(同一セッション内で実行) を推奨します。シンプルだし、Claude Code なら Bash ツールでファイル操作もできるので、エージェント本文は大体こなせるはず。
